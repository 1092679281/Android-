# R18 — 别克君越 E2LB：本机蓝牙地址与当前 CarPlay 会话身份一致性

## 来自 15:27 实车日志的新证据

- 截图（15:29）显示「本机蓝牙地址：已就绪（手动填写）」，但 **15:27:19 已经发起的那一轮**却明确输出：
  `CTRL: 蓝牙 MAC 解析为占位值`；`BT: 未能解析真实蓝牙 MAC`。
- 当时 iAP2 对端是 `model=E2LB manufacturer=Saic General Motors`，执行 `0x4300` 后没有收到对端承诺会发送的 `0x4301`。
- 本机的 DeviceIdentity 手动保存功能能使设置界面变绿，但 **已经发出的 0x4300（含本机蓝牙身份）以及当时发布的 TXT id 都不会因为后来保存设置自动改写**。即使后来输入正确地址，已启动的会话仍按旧身份走，需要取消并发起一轮新的连接。
- 同时看到了主动 BT-C 与被动车机回连 BT 的交错：其中一条会话协商超时，另一条已完成 iAP2。它不是当前唯一故障证据，不应误判为整个蓝牙通信失败。
- 当时 iAP2 的 MFi `0xaa05` 为 `RESPONSE_UNVERIFIED`，真实车机未承诺接受完整 CarPlay 会话。即使解决 MAC，一样需要真实 `0x4301`、SETUP/RECORD 和车机显示验证。

## R18 改动

- `SessionController.startConnection` 启动 ctrl TXT 广播和 RFCOMM 之前同步读取当前已保存身份，输出 `IDENTITY: 本轮启动地址 source=... placeholder=...`，避免误将「后续设置页显示已就绪」理解为「本轮也已发送有效地址」。
- `BtSession.resolveBluetoothMac` 对从内存缓存取得的身份**也输出证据行**，明确真正用于 0x4300/0x4e0e 的 MAC 来源，原先读取缓存时静默返回，难以交叉核对。
- 用户在「本机蓝牙地址」设置页**连接过程中**保存/清除身份，如果与当轮启动快照不同，立即提示「取消连接后重新连接」；不会静默更改当前会话已发送的 0x4300，也不在连接过程中擅自重启蓝牙或丢弃 CarWith 状态。
- `BluetoothIdentitySessionPolicyTest` 复现占位身份→手动真实身份、大小写规范化、手动值修改等情景。
- 保留稳定的 R16 SETUP500、R15 在线更新和 R14 SETUP/RECORD 检验，不合并尚在调试中的 R17 模拟环境。

## 停车状态实车复测

1. **先取消当前连接**。在「本机蓝牙地址」中查看已保存的本机手机地址；不要填车机蓝牙地址。
2. 保存后从连接首页重新点「启动连接」。检查在车机识别前出现 `IDENTITY: 本轮启动地址 source=手动填写 placeholder=false`。
3. 核对 `CTRL: ... id=...` 与 `BT: 本机蓝牙 MAC=... 来源=手动填写` 一致。如仍为 placeholder=true，不要将设置页绿灯视为旧会话身份已经更新。
4. 继续看 0x4300 以后是否收到 0x4301 或新的 ctrl 邀请、_airplay._tcp 是否出现、AirPlay 初始 SETUP 是否从 500 变为 200。即使新版报告身份一致，也不保证真正的 GM E2LB 固件接受协议。
5. 如果 0x4301 一直不发，下一步应分析车机对无线 CarPlay/MFi 的信任、0x4300 字段和真实车机身份协商，而不是继续仅修改 RECORD。
